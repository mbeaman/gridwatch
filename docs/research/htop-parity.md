# htop 3.4.1 as an opsTui component — research write-up

Everything below was checked against the installed `htop 3.4.1` (Ubuntu 3.4.1-5build2, `man htop`, `~/.config/htop/htoprc`), the htop 3.4.1 sources on GitHub, docs.rs pages for the exact crate versions, and read-only probes of torch on 2026-08-30.

## 1. What htop 3.4.1 actually does (inventory)

### 1.1 Header meters (Linux `Platform_meterTypes`)
CPU, Clock, Date, DateTime, LoadAverage, Load, Memory, Swap, MemorySwap, SysArch, HugePage, Tasks, Uptime, Battery, Hostname, AllCPUs/AllCPUs2/AllCPUs4/AllCPUs8, LeftCPUs/RightCPUs (and 2/4/8 variants), Blank, PressureStallCPUSome, PressureStallIOSome, PressureStallIOFull, PressureStallIRQFull, PressureStallMemorySome, PressureStallMemoryFull, ZfsArc, ZfsCompressedArc, Zram, DiskIO, NetworkIO, SELinux, Systemd, SystemdUser, FileDescriptor, GPU. Each meter has a mode: **Bar, Text, Graph, LED**. Header layouts (13): one_100, two_50_50 (default), two_33_67, two_67_33, three_33_34_33, three_25_25_50, three_25_50_25, three_50_25_25, three_40_30_30, three_30_40_30, three_30_30_40, three_40_20_40, four_25_25_25_25. Default meters on a 17–32 CPU box are `LeftCPUs4 Memory Swap | RightCPUs4 Tasks LoadAverage Uptime` (Settings.c; torch's htoprc matches). Default `delay=15` tenths = **1.5 s**.

**CPU meter semantics** (`CPUMeter.c`, `LinuxMachine.c`). Per-CPU line of `/proc/stat` is parsed into user, nice, system, idle, iowait, irq, softirq, steal, guest, guest_nice; then `user -= guest; nice -= guest_nice` (kernel double-counts guest inside user). Aggregates: `systemall = system+irq+softirq`, `idleall = idle+iowait`, `virt = guest+guest_nice`, `total = user+nice+systemall+idleall+steal+virt`. Deltas are `saturating_sub` against the previous scan; every segment is `delta/totalPeriod*100`. Segment/colour order (`CPUMeter_attributes`): nice=**bold blue**, normal(user)=**green**, system=**red**, irq=**yellow**, softirq=**magenta**, steal=**cyan**, guest=**cyan**, iowait=**bold grey**. With `detailed_cpu_time=0` (default) the bar has 4 segments: nice, user, kernel(=system+irq+softirq), virt(=steal+guest; shown only if `account_guest_in_cpu_meter`); iowait is NOT drawn (it is treated as idle). Detailed text mode prints `%5.1f%%` per class with labels sy/ni/hi/si/st/gu/wa. Optional suffixes in the bar text: `%4uMHz` and `%d°C`. Caption is `Avg` for the aggregate or `%3u` CPU id (`cpu_count_from_one` option). Bar chars: colour mode fills with `|`; mono mode uses `"|#*@$%&."` per segment; graph mode is 4 rows tall using braille cells (2 samples per column), ASCII fallback `" .:"`.

**Memory meter** (`LinuxMachine_scanMemoryInfo` + `MemoryMeter.c`): reads MemTotal, MemFree, MemAvailable, Buffers, Cached, Shmem, SReclaimable, SwapTotal, SwapFree, SwapCached, Zswap, Zswapped. Formulas:
```
cached    = Cached + SReclaimable - Shmem
used      = MemTotal - (MemFree + Cached + SReclaimable + Buffers)   // fallback MemTotal-MemFree
available = min(MemAvailable, MemTotal)                              // MemFree if absent
usedSwap  = SwapTotal - SwapFree - SwapCached ; cachedSwap = SwapCached
compressed(zswap) = Zswap (orig Zswapped); zram from /sys/block/zram*/{mm_stat,disksize}
```
Bar segments in order: used=**green**, shared=**magenta**, compressed=**bold grey**, buffers=**bold blue**, cache=**yellow**; bar text `"{used+shared+compressed}/{total}"` via `Meter_humanUnit` (K/M/G/T, 2/1/0 decimals for <10/<100/>=100). Text mode labels: `used: shared: compressed: buffers: cache: available:` (cache/buffers hidden when `show_cached_memory=0`). **Swap meter**: used=**red**, cache=**yellow**, frontswap(zswap)=**bold grey**; text `used: cache: frontswap:`.

**Other meters**: LoadAverage `"%.2f/%.2f/%.2f"` (1-min bold white, 5-min bold cyan, 15-min cyan); OK/WARN/ERROR by 1-min load `<1`, `<activeCPUs`, else, with bar totals 1/cpus/2×cpus. Tasks: `"{procs}, {uthreads} thr, {kthreads} kthr; {running} running"` (hidden classes drawn shadowed; running capped at activeCPUs). Uptime `"{N} days(!), HH:MM:SS"` ("(!)" past 100 days). DiskIO: `/proc/diskstats`, sectors×512, skips partitions, `dm-*` and `zram*`; text `r:XiB/s w:XiB/s U%`, utilisation = `100*Δms_busy/Δwall` summed over disks (may exceed 100%; bar uses per-disk normalised value), notice colour above 40%. NetworkIO: `/proc/net/dev` skipping `lo`, recomputed every 500 ms, `rx:XiB/s tx:XiB/s N/Mpkts/s`. PSI: `/proc/pressure/{cpu,io,memory,irq}` avg10/avg60/avg300 (colours bold white / bold cyan / cyan). FileDescriptor: `/proc/sys/fs/file-nr` used/max. Battery: `/sys/class/power_supply/*/uevent` (10 s cache). CPU frequency: `/sys/devices/system/cpu/cpuN/cpufreq/scaling_cur_freq` (kHz→MHz), fallback `/proc/cpuinfo "cpu MHz"`; index 0 = mean. CPU temperature: dlopen `libsensors.so[.5|.4]`; recognises coretemp/k10temp/zenpower…; matches labels `Package id`, `Physical id`, `Core N`, `Tccd*` only (not Tctl/Tdie); Tccd temps are assigned to CPUs by a "coresPerCCD = existingCPUs/#Tccd, assigned in core-id order" hypothesis; package temp = max of per-core values when missing. GPU meter (new in 3.4.0): sums `drm-engine-*` nanoseconds from `/proc/[pid]/fdinfo/*`, `GPU% = 100*Δns/1e6/Δmonotonic_ms`, up to 4 engines + residue.

### 1.2 Process table
Default Main screen columns: `PID USER PRIORITY NICE M_VIRT M_RESIDENT M_SHARE STATE PERCENT_CPU PERCENT_MEM TIME Command`; default I/O screen: `PID USER IO_PRIORITY IO_RATE IO_READ_RATE IO_WRITE_RATE PERCENT_SWAP_DELAY PERCENT_IO_DELAY Command`. Key formulas (`LinuxProcessTable.c`):
```
period      = Δ(total jiffies of the aggregate "cpu" line) / activeCPUs
percent_cpu = Δ(utime+stime) / period * 100, clamped to activeCPUs*100   // "Irix mode"
NCPU%       = percent_cpu / activeCPUs                                     // "Solaris mode"
percent_mem = rss_kb / MemTotal_kb * 100
io_rate     = Δread_bytes * 1000 / Δrealtime_ms   (NaN -> "N/A")
TIME+       = (utime+stime) as centiseconds; starttime = btime + starttime/CLK_TCK
```
Files read per scan: always `stat`, `statm`, `status`; only when the column is enabled: `cgroup`, `smaps_rollup` (PSS/SWAP/PSSWP), `io`, `oom_score`, `attr/current`, `cwd`, `exe`, `autogroup`; `cmdline`/`comm` on first sight or with `update_process_names`. Threads come from recursing `task/`; kernel thread ⇔ `PF_KTHREAD (0x00200000)` in stat field 9; userland thread ⇔ pid ≠ tgid. Rendering rules worth copying exactly: `Row_printPercentage` — `<0.05` shadow, `>=99.9` cyan, MEM% width 4 prints `100`; `Row_printKBytes` — `<1000` plain, `<100000` "MM" cyan + "KKK", else 3-significant-digit `97.6M / 9.76G / 100G / 1000G` with colour cycling plain→cyan(M)→green(G)→LARGE_NUMBER(T); `Row_printTime` — `MM:SS.hh`, `HHhMM:SS`, `DdHHhMMm`, `DDDDdHHh`, `YYYyDDDd`; STARTTIME `%R` (<24 h), `%b%d` (<1 y), ` %Y`; NICE `<0` red / `>0` green / 0 shadow; PRIORITY `RT` when `<= -100`; STATE R/T(traced) green, D/Z/T(stopped)/X bold red; USER shadowed if not htop's uid, magenta if elevated capabilities; NLWP shadowed when 1; threads green, basename bold cyan, deleted exe red; tagged rows bold yellow; new/tomb rows black-on-green / black-on-red (`highlight_changes`, `-H`); selection black-on-cyan; function bar black-on-cyan: `F1Help F2Setup F3Search F4Filter F5Tree F6SortBy F7Nice- F8Nice+ F9Kill F10Quit` (7–9 blank in `--readonly`).

Interactive features (Action.c + man): Up/Down/PgUp/PgDn/Home/End, Left/Right (horizontal scroll, Ctrl-A/^ and Ctrl-E/$), Space tag, `c` tag+children, `U` untag, `s` strace, `l` lsof, `w` wrapped cmdline, `x` file locks, `e` environment, F1/h/? help, F2/S/C setup, F3// incremental search (Shift-F3 backwards), F4/\ filter (case-insensitive fixed strings, `|` = OR, 128 chars), F5/t tree (`+`/`-`/`=`/`*` expand/collapse, Backspace collapse-into-parent), F6/</>/,/. sort column, F7/] renice up, F8/[ renice down, Shift-F7/} and Shift-F8/{ autogroup nice, F9/k kill (signal menu, 31 signals SIGHUP..SIGSYS), F10/q quit, `I` invert sort, `a` affinity, `i` I/O priority, `Y` scheduling policy, `u` user filter, `N`/`M`/`P`/`T` sort by PID/mem/CPU/time, `F` follow, `K` hide kernel threads, `H` hide userland threads, `O` hide containerised, `p` program path, `m` merge exe/comm/cmdline, `Z` pause, `#` hide meters, Ctrl-L redraw, digits = PID search, Tab/Shift-Tab screen tabs, mouse (click header to sort, click row). Multiple screens ("Main", "I/O") each with own columns/sort. Privileged actions: `ioprio_set(IOPRIO_WHO_PROCESS=1, pid, (class<<13)|level)` with classes NONE=0 RT=1 BE=2 IDLE=3 and levels 0–7 (column shows `B4`, `R0`, `id`; for class NONE it prints `B{(nice+20)/5}`); `setpriority`; `sched_setaffinity(pid)` (hwloc optional); autogroup via read/write of `/proc/[pid]/autogroup` (`/autogroup-N nice M`); CPUD%/IOD%/SWAPD% need libnl taskstats + CAP_NET_ADMIN. **Ubuntu's htop binary links only ncursesw/tinfo** — no libnl, libcap, hwloc; libsensors/libsystemd are dlopen'd (libsensors.so.5 is present on torch, so temperatures work if enabled).

## 2. Linux data sources and Rust access

### 2.1 Direct files (all verified on torch)
`/proc/stat` (aggregate + 32 `cpuN` lines, 10 fields; also `procs_running`, `ctxt`, `btime`), `/proc/meminfo`, `/proc/loadavg` (`3.63 3.29 3.12 9/2338 337146`), `/proc/pressure/{cpu,io,memory}` (**no `irq`** on torch — CONFIG_IRQ_TIME_ACCOUNTING is not set), `/proc/uptime`, `/proc/diskstats`, `/proc/net/dev`, `/proc/sys/fs/file-nr`, `/proc/[pid]/{stat,statm,status,cmdline,comm,io,cgroup,oom_score,autogroup,schedstat,smaps_rollup,task/*}`, `/sys/devices/system/cpu/cpuN/cpufreq/{scaling_cur_freq,cpuinfo_avg_freq,amd_pstate_prefcore_ranking,energy_performance_preference}`, `/sys/class/hwmon/hwmon4` (k10temp: `temp1_label=Tctl`, `temp3_label=Tccd1`, `temp4_label=Tccd2` — **temp2 is absent; parse by label, never assume contiguous indices**), `/sys/class/powercap/intel-rapl:0` (package-0) and `intel-rapl:0:0` (core). Units: CLK_TCK=100 (jiffies are centiseconds — TIME+ needs no scaling), PAGESIZE=4096, cpufreq in kHz, hwmon in millidegrees, RAPL in µJ with `max_energy_range_uj=65532610987` (wrap!). No zram, no zswap (`N`), no battery, swap is a 16 GiB file, cgroup v2.

### 2.2 procfs 0.18.0 (recommended for the process table)
`procfs = "0.18.0"` (+ `procfs-core 0.18.0`, MSRV 1.70, default features `chrono`, `flate2`). Reading is via traits: `use procfs::{Current, CurrentSI};` then `KernelStats::current()` → `{ total: CpuTime, cpu_time: Vec<CpuTime>, ctxt, btime, processes, procs_running: Option<u32>, procs_blocked }` with `CpuTime { user, nice, system, idle: u64, iowait, irq, softirq, steal, guest, guest_nice: Option<u64> }` (ticks; `*_ms()`/`*_duration()` helpers). `Meminfo::current()` (all values in **bytes**; `mem_available`, `shmem`, `s_reclaimable`, `z_swap`, `z_swapped` are `Option`). `LoadAverage::current()`. `CpuPressure/MemoryPressure/IoPressure::current()` → `{ some, full: PressureRecord { avg10, avg60, avg300: f32, total: u64 } }` (no IRQ struct — read `/proc/pressure/irq` yourself if it ever appears). `procfs::process::all_processes() -> ProcResult<ProcessesIter>` yielding `Result<Process, ProcError>` (`PermissionDenied | NotFound | Incomplete | Io | Other | InternalError`; vanished pids surface as `NotFound`). `Process` (holds a dirfd; torch soft nofile is 524288 so keeping 636 open is fine, but re-create per tick anyway to dodge PID reuse): `stat() -> Stat` (all 52 fields: `utime, stime, cutime, cstime, priority, nice, num_threads, starttime, vsize, rss(pages), processor, rt_priority, policy, delayacct_blkio_ticks, guest_time`, plus `state() -> ProcState`, `flags() -> StatFlags` for PF_KTHREAD, `rss_bytes()`), `statm() -> StatM { size, resident, shared, text, lib, data, dt }` (pages → SHR/CODE/DATA), `status() -> Status` (`ruid/euid`, `tgid`, `nspid`, `threads`, `vmrss/vmswap` in kB, `voluntary/nonvoluntary_ctxt_switches`, `cpus_allowed_list`, capability masks for the "elevated" colouring), `io() -> Io { rchar, wchar, syscr, syscw, read_bytes, write_bytes, cancelled_write_bytes }`, `cmdline()`, `exe()`, `cwd()`, `cgroups()`, `oom_score()`, `autogroup() -> String`, `schedstat()`, `smaps_rollup()`, `tasks() -> TasksIter` of `Task { pid, tid }` with `stat()/status()/io()/schedstat()`. Helpers: `procfs::ticks_per_second()`, `page_size()`, `boot_time_secs()`, `diskstats()`, `procfs::net::dev_status()`, `CpuInfo::current()`, `Uptime::current()`.

Shape of the sampler (std thread, snapshot per tick):
```rust
#[derive(Clone, Copy, Default)]
struct CpuTicks { user:u64, nice:u64, sys:u64, idle:u64, iowait:u64, irq:u64, softirq:u64, steal:u64, guest:u64, gnice:u64 }
impl From<&procfs::CpuTime> for CpuTicks { /* subtract guest from user, guest_nice from nice, like htop */ }
struct CpuBreakdown { nice:f32, user:f32, kernel:f32, irq:f32, softirq:f32, steal:f32, guest:f32, iowait:f32, idle:f32 } // % of totalPeriod

fn breakdown(prev:&CpuTicks, cur:&CpuTicks) -> CpuBreakdown {
    let d = |a:u64,b:u64| a.saturating_sub(b) as f32;
    let total = d(cur.total(), prev.total()).max(1.0);
    CpuBreakdown { user: d(cur.user,prev.user)/total*100.0, /* … */ }
}

struct ProcSample { pid:i32, tgid:i32, ppid:i32, uid:u32, comm:String, cmdline:Vec<String>, state:char,
    kthread:bool, prio:i64, nice:i64, nlwp:i64, cpu_ticks:u64, starttime:u64, vsize:u64, rss_pages:u64,
    shared_pages:u64, processor:Option<i32>, io:Option<procfs::process::Io>, cgroup:Option<String>, oom:Option<u16> }

fn percent_cpu(prev:Option<u64>, cur:u64, period:f32, active_cpus:u32) -> Option<f32> {
    prev.map(|p| ((cur.saturating_sub(p) as f32) / period * 100.0).min(active_cpus as f32 * 100.0))
}
```
Measured cost on torch (636 processes, 2346 threads, 431 kernel threads, 152 own): one pass over every `/proc/[pid]/stat`, `statm`, `status`, `cmdline`, `cgroup`, `oom_score`, `autogroup`, `comm`, `schedstat` each completes in under 10 ms wall; all `task/*/stat` 10 ms, `task/*/status` 20 ms; `/proc/stat + meminfo + loadavg + 3 PSI files` ≈ 0.9 ms per tick; 32× `scaling_cur_freq` ≈ 2 ms; `smaps_rollup` for the 152 readable processes = **130 ms** (PSS/SWAP columns must be on-demand, exactly as htop gates them). So a full htop-parity scan is ~30–60 ms single-threaded at a 1.5 s tick — rayon is unnecessary; keep the sampler off the UI thread.

Actions (nix 0.31.3): `nix::sys::signal::kill(Pid::from_raw(pid), Signal::SIGTERM)` (feature `signal`); `nix::sched::{sched_getaffinity(pid) -> Result<CpuSet>, sched_setaffinity(pid, &CpuSet)}` (feature `sched`; Linux applies to a single tid — htop sets the main pid only); renice via `libc::setpriority(libc::PRIO_PROCESS, pid as libc::id_t, nice)` (nix 0.31 has no setpriority wrapper); I/O priority via `libc::syscall(libc::SYS_ioprio_set, 1 /*IOPRIO_WHO_PROCESS*/, pid, (class << 13) | level)`; autogroup nice by writing the integer to `/proc/[pid]/autogroup`; uid→name via `uzers 0.12.2` (`UsersCache` + `Users::get_user_by_uid`).

### 2.3 sysinfo 0.39.6 — what it gives and lacks
MSRV **1.95** (exactly torch's toolchain). Default features `component, disk, network, system, user`; **`multithread` (rayon) is opt-in in 0.39** (verified in Cargo.toml). API: `System::new_with_specifics(RefreshKind)`, `refresh_specifics`, `refresh_cpu_specifics(CpuRefreshKind::nothing().with_cpu_usage().with_frequency())`, `refresh_memory_specifics`, `refresh_processes_specifics(ProcessesToUpdate::All, remove_dead: bool, ProcessRefreshKind) -> usize`; `ProcessRefreshKind::nothing().with_cpu().with_memory().with_disk_usage().with_user(UpdateKind::OnlyIfNotSet).with_cmd(UpdateKind::OnlyIfNotSet)` (avoid `.with_tasks()`/`everything()` — docs warn it walks every `task/<tid>`). `Process`: `name() -> &OsStr` (15-char comm), `cmd`, `exe`, `cwd`, `memory()` (RSS bytes), `virtual_memory`, `parent`, `status`, `start_time`, `run_time`, `cpu_usage() -> f32` (Irix-mode, up to ncpu×100 — computed as Δ(utime+stime)/(Δtotal/ncpu)×100, identical to htop), `accumulated_cpu_time()` ms, `disk_usage() -> DiskUsage { read_bytes, total_read_bytes, written_bytes, total_written_bytes }` (**delta per refresh, not per second**), `user_id`, `effective_user_id`, `session_id`, `tasks() -> Option<&HashSet<Pid>>`, `thread_kind() -> Option<ThreadKind>`, `kill_with(Signal) -> Option<bool>`, `open_files`. `Cpu::cpu_usage()` (0–100 per core, first refresh is 0, `MINIMUM_CPU_UPDATE_INTERVAL = 200 ms`), `frequency()` MHz (scaling_cur_freq → /proc/cpuinfo fallback), `brand()`. `Components` labels are `"{hwmon name} {label}"` (so `"k10temp Tctl"`, `"k10temp Tccd1"`) with `temperature() -> Option<f32>`, `max`, `critical`, `id`. Memory: `used = MemTotal − MemAvailable` (not htop's formula; buffers/cache/shared not separated).

Per-core usage in sysinfo = `(Δuser+Δnice+Δ(system+irq+softirq)+Δsteal+Δguest)/Δtotal` — a single number; **no per-class breakdown, no guest subtraction**. Missing vs htop: per-core nice/user/kernel/irq/softirq/iowait/steal segments, buffers/cache/shared/zswap split, PSI, load thresholds, process nice/priority/RT, state char beyond `ProcessStatus`, SHR/CODE/DATA, NLWP without tasks, TTY, last CPU, minflt/majflt, ctxt switches, cgroup/container, OOM score, ioprio, autogroup, PSS/swap, cutime/cstime, GPU fdinfo, delay accounting, IO rates as B/s. Verdict: sysinfo is fine for a 1x1/2x1 "CPU% + mem" tile and for the temperature/network/disk helpers, but the htop component needs procfs-core plus hand-rolled deltas; do not mix both samplers for the same numbers.

### 2.4 Permissions on torch (user mattbeam, groups incl. i2c; no caps on htop; `hidepid` not set)
All 636 pids are listable; `stat/statm/status/cmdline/cgroup/oom_score/comm` readable for everyone; `io`, `exe`, `cwd`, `environ`, `smaps_rollup`, `fdinfo` only for own-uid processes (`/proc/1/io` → EACCES; `ptrace_scope=1` does not block PTRACE_MODE_READ for same-uid). 472 processes are root's, so IO-rate/EXE columns will be `N/A` for ~75 % of rows — same as htop. Kill/renice/affinity/ioprio on own processes only; raising priority (nice<0), RT ioprio and other users' processes need root/CAP_SYS_NICE/CAP_SYS_ADMIN. Delay accounting is off (`kernel.task_delayacct=0`, no libnl in Ubuntu's htop either). RAPL `energy_uj` is mode 0400 root (kernel 5.10 commit 949dd0104c49, CVE-2020-8694 "PLATYPUS") and `perf_event_paranoid=4` blocks the perf `power/energy-pkg/` PMU, so package watts need a udev rule (`chmod 0444` on `intel-rapl:0/energy_uj`) or a root helper — nothing in hwmon exposes CPU power (k10temp has temps only; no zenpower). `/sys/module/nvidia_drm/parameters/modeset` is also root-only. GPU: **no `drm-*` fdinfo on any own process, including the running game (12.5 GiB VRAM)** — htop's GPU meter/GPU% column will be N/A with the NVIDIA proprietary driver; use NVML per-process accounting in the nvtop component instead.

## 3. Size-class plan for the htop component
Assume a grid cell ≈ 20 cols × 6 rows (tune once the layout engine exists); each footprint declares `min_cols × min_rows` and the component picks the richest variant that fits.
- **1×1 (≈20×6)**: title, big `37.2%` total-CPU number (tui-big-text or plain bold), a 1-row `Sparkline` of total CPU (ring buffer of ~120 samples), second row `mem 21% · load 3.6`. Colour by htop's OK/WARN/ERROR thresholds. Data: `/proc/stat` aggregate + meminfo + loadavg only (0.1 ms).
- **2×1 (≈40×6)**: left: CPU sparkline + per-class stacked bar (nice/user/kernel/virt in htop colours) for the aggregate; right: memory stacked `LineGauge`-style bar (`used|shared|buffers|cache` segments — needs a custom `StackedBar` widget, ratatui's `Gauge/LineGauge` are single-segment), swap bar, `Tasks 636, 1911 thr, 431 kthr; 5 running`, `Load 3.63/3.29/3.12`, uptime.
- **4×2 (≈80×12)**: per-core bars: two CCD blocks × 8 cores, each core row shows its SMT pair (cpu N | cpu N+16) as two short bars, CCD temperature (`Tccd1/Tccd2`) and mean frequency in the block header; memory/swap bars; load/tasks/uptime line; optional PSI mini-row (`cpu some 0.00 · io some 0.00 · mem some 0.00`).
- **6×3 (≈120×18)**: everything above in the top ~7 rows plus a top-N process table (N = remaining rows − header) with `PID USER CPU% MEM% RES S TIME+ Command`, sortable, selectable, tag/kill enabled.
- **Full / zoomed**: header meters in a configurable 2-column layout, complete process table with all columns and per-screen tabs (Main / I/O), tree view, search/filter, F-key bar, affinity/ioprio/renice/kill modals — i.e. htop parity with theme colours mapped from the attribute table in §1.
Degradation rules: drop columns in the order VIRT, SHR, PRI, NI, S, RES, TIME+, USER, PID, MEM%, CPU% (Command always last and elastic); per-core bars → per-CCD aggregates → one aggregate bar; graph mode (braille) → bar → text → LED digits (the LED mode is a gift for the retrowave theme); when width < 30, hide the bar text suffixes (MHz/°C) first. All modes read from the same `Arc<Snapshot>`; only the full mode turns on the expensive per-column files.

## 4. Interaction design inside the grid
- Two-level focus: grid focus (Tab/Shift-Tab or hjkl move between components; `Enter`/`z` zooms the focused component to full-screen, `Esc` un-zooms) and component focus (the htop component captures keys after `Enter`; `Esc` returns focus to the grid). Show a one-line htop-style function bar only while focused, in the theme's bar colour.

## 5. Torch-specific (Zen 5, family 26 model 68, "AMD Ryzen 9 9950X3D2 16-Core")
- Topology (sysfs): 16 cores / 32 threads; SMT sibling of cpu N is cpu N+16; `die_id` 0 = cpus 0–7,16–23 (core ids 0–7), `die_id` 1 = cpus 8–15,24–31 (core ids 8–15). `lscpu` reports **L3 = 2 × 96 MiB (192 MiB total)**, i.e. both CCDs carry 3D V-Cache on this part (a 9950X3D has 96 + 32) — so "which cores are V-cache" = all of them; I cannot vouch for product-marketing details past my knowledge cutoff, only for what sysfs shows.
- htop's CCD hypothesis (`coresPerCCD = 32 logical / 2 Tccd = 16`, assigned in core-id order) happens to produce CCD0 = {0–7,16–23}, CCD1 = {8–15,24–31}, which matches the real die map — so htop's per-core temperature attribution is correct here; opsTui should read `topology/die_id` directly instead of guessing.
- k10temp (hwmon4): `Tctl` (temp1, control temperature; equals Tdie on Zen 5 desktop, no offset), `Tccd1` (temp3), `Tccd2` (temp4); readings 59.3 / 59.0 / 53.1 °C during the game. No fan sensors, no Vcore/Icore.
- cpufreq: driver `amd-pstate-epp` (active mode), governor `powersave`, EPP `balance_performance`, boost on, 32 independent policies, `scaling_cur_freq` present (5.5 GHz under load), `cpuinfo_cur_freq` absent, `cpuinfo_avg_freq` present (hardware-derived), `/proc/cpuinfo "cpu MHz"` live. `amd_pstate_prefcore_ranking` (higher = preferred): CCD0 cores 206–236, CCD1 166–201, `amd_pstate_highest_perf = 166` everywhere → the scheduler prefers CCD0; `amd_x3d_vcache` driver present, `AMDI0101:00/amd_x3d_mode = "frequency"` (values `frequency|cache`, kernel ≥ 6.13, root-writable) — worth a status glyph in the CPU header.
- RAPL: `intel_rapl_msr` on AMD exposes `package-0` and `core` domains; root-only as noted. Kernel config: PSI=y, TASK_DELAY_ACCT=y (runtime off), SCHED_AUTOGROUP=y (on), HZ=1000, AMD_3D_VCACHE=m, INTEL_RAPL=m.
- Terminal: VTE/Ptyxis with DejaVu Sans Mono renders braille (U+2800) and block elements fine, so htop-style graph mode works without Nerd Fonts; keep an ASCII fallback (`-U` equivalent).

## Recommendations

- **Build the htop component's sampler on procfs-core 0.18 (+ hand-rolled deltas), not sysinfo.** — htop parity needs per-core class breakdown (nice/user/kernel/irq/softirq/steal/guest/iowait), htop's memory formula (Cached+SReclaimable−Shmem etc.), PSI, nice/priority/state/NLWP/SHR/TTY/processor/ctxt/cgroup/OOM/ioprio/autogroup and per-second IO rates. sysinfo 0.39.6 exposes only one usage % per core and 'used = total − available', and hides most process fields. procfs gives every /proc file as a typed struct (Stat with all 52 fields, StatM, Status, Io, CpuTime, Meminfo, pressure structs) and a full scan costs tens of milliseconds on torch.
  - alternatives: sysinfo 0.39.6 with ProcessRefreshKind::nothing().with_cpu().with_memory() for the 1x1/2x1 tiles only (its process cpu_usage() is numerically identical to htop's CPU%); raw std::fs parsing of /proc without procfs (more code, no benefit).
- **Run the sampler on a std thread at htop's default 1.5 s and publish immutable Arc<Snapshot>s; gate expensive files (smaps_rollup, io, cgroup, oom_score, autogroup, exe/cwd) on enabled columns exactly like htop's PROCESS_FLAG_* checks.** — Measured on torch: stat/statm/status/cmdline for all 636 pids each < 10 ms; smaps_rollup for the 152 readable pids = 130 ms; per-tick meters < 1 ms. Keeping the UI thread free of /proc I/O keeps tachyonfx/animations smooth; rayon (sysinfo's non-default `multithread`) is unnecessary at this scale.
  - alternatives: tokio task with spawn_blocking (fine if the rest of opsTui is tokio-based; the sampler itself is synchronous file I/O either way); per-column lazy reads only when a row is visible (more complex, marginal gain).
- **Define the CPU meter as a reusable StackedBar widget with htop's segment order and colours mapped through the theme (nice/user/kernel/irq/softirq/steal/guest/iowait), with modes Bar / Text / Graph(braille) / LED, and lay the 32 threads out as 2 CCD blocks × 8 cores × SMT pair using sysfs topology (die_id, thread_siblings_list) rather than htop's coresPerCCD guess.** — ratatui 0.30.2 has no multi-segment gauge (Gauge/LineGauge are single-ratio); htop's visual identity is the 4-segment bar. Torch's CCD map is cpus 0-7,16-23 vs 8-15,24-31 with SMT sibling N+16; grouping by CCD lets Tccd1/Tccd2 temperatures and prefcore ranking sit next to the right cores. LED mode doubles as the retrowave look.
  - alternatives: ratatui BarChart with Bar/BarGroup (vertical only, no stacking); tui-widgets extras; per-core Sparklines instead of bars for the graph mode.
- **Expose footprints 1x1 (CPU% number + sparkline), 2x1 (+ stacked CPU/mem/swap bars, tasks/load/uptime), 4x2 (+ per-core CCD blocks, PSI row), 6x3 (+ top-N process table), Full/zoom (complete htop parity with screens, tree, F-key bar and modals); declare min cols/rows per footprint and degrade columns in the order VIRT, SHR, PRI, NI, S, RES, TIME+, USER, PID, MEM%, CPU% with Command always last.** — Matches the product goal of re-arrangeable components with several footprints; each footprint reads the same snapshot so switching is free, and only Full turns on the costly per-column files.
  - alternatives: A single responsive renderer that hides pieces by area (harder to test and theme); separate components for 'CPU meter', 'memory meter' and 'process table' composed by the user (more flexible, but loses the htop identity; could be offered later as sub-components).
- **Adopt htop's key bindings verbatim inside the focused component (Space/c/U tags, </>/F6 sort, I invert, P/M/T/N, t tree, / search, \ filter with '|' OR, F follow, K/H toggles, u user filter, a affinity, i ioprio, F7/F8 renice, F9/k kill), add a grid-level Enter/Esc focus model and a zoom key, and add a kill confirmation plus a global readonly flag that blanks F7–F9 like htop --readonly.** — Muscle-memory parity is the point of an htop clone; the dashboard context (a game running, other tiles) justifies a confirmation step htop lacks. Key state must be keyed by PID (selection, tags, collapsed subtrees) so re-sorts do not move the cursor.
  - alternatives: Vim-only navigation with a command palette (nicer for the themed product, but breaks htop parity; can be an additional layer); no process actions at all in v0.x (defer nix/libc syscalls to a later arc).
- **Implement process actions with nix 0.31.3 (features signal, sched) for kill/affinity, libc 0.2 for setpriority and the raw ioprio_set syscall ((class<<13)|level, IOPRIO_WHO_PROCESS=1), and plain file writes for /proc/[pid]/autogroup; resolve user names with uzers 0.12.2 behind a UsersCache.** — These mirror exactly what htop 3.4.1 calls (sched_setaffinity, setpriority, ioprio_set, fopen r+ on autogroup) and need no extra system packages. nix 0.31 has no setpriority wrapper; libc's stable line is 0.2.x (cargo search shows a 1.0.0-alpha.4 prerelease — do not depend on it).
  - alternatives: sysinfo's Process::kill_with(Signal) (only kill); shelling out to renice/taskset/ionice/chrt (all present on torch, but slower and harder to report errors from).
- **Treat package power (RAPL) and per-process GPU% as optional, initially absent, features: read /sys/class/powercap/intel-rapl:0/energy_uj only if readable (document the udev chmod 0444 rule or a root helper), and skip htop's fdinfo GPU meter entirely on this host.** — energy_uj is 0400 root since kernel 5.10 (PLATYPUS mitigation) and perf_event_paranoid=4 blocks the perf RAPL PMU; the NVIDIA proprietary driver exposes no drm-* fdinfo (verified 0 files across own processes including the running game), so htop's own GPU meter would show N/A here. NVML (nvml-wrapper) belongs to the nvtop component.
  - alternatives: A setuid/systemd helper exporting energy via Prometheus like astral-watch's exporter; msr reads (also root); zenpower out-of-tree module (not installed, questionable Zen 5 support).

## Risks

- **Sampling deltas across PID reuse or first tick: CPU% and IO rates need the previous sample; a reused PID with a smaller utime+stime would produce garbage or negative values.** → Key history by (pid, starttime) not pid alone; use saturating_sub everywhere like htop; render '—'/N/A until two samples exist; re-create procfs::Process each tick instead of holding dir fds.
- **Permissions: ~75% of rows on torch are root-owned, so /proc/[pid]/io, exe, cwd, environ, smaps_rollup and fdinfo return EACCES and kill/renice/affinity fail with EPERM; RAPL energy_uj is root-only (0400) and perf_event_paranoid=4 blocks the perf fallback.** → Show htop-style shadowed 'N/A' and never treat EACCES as fatal; surface EPERM as a toast; make power and IO columns optional; document a udev rule (chmod 0444 on intel-rapl:0/energy_uj) or a root helper for watts.
- **smaps_rollup (PSS/SWAP/PSSWP columns) costs ~130 ms for only the readable processes on torch and scales with mapped memory; polling it every tick would stall the sampler and burn CPU while a game runs.** → Gate on column visibility exactly like htop (PROCESS_FLAG_LINUX_SMAPS), sample it at a lower rate, and only for visible rows.
- **hwmon index assumptions: k10temp on torch exposes temp1 (Tctl), temp3 (Tccd1), temp4 (Tccd2) with no temp2; a parser assuming contiguous tempN indices or fixed positions silently mislabels CCD temperatures.** → Enumerate temp*_label files and map by label; map CCDs to cores via /sys/devices/system/cpu/cpuN/topology/die_id instead of htop's coresPerCCD heuristic.
- **htop's GPU meter/GPU% relies on DRM fdinfo which the NVIDIA proprietary driver does not expose (verified: zero drm-* fdinfo entries on own processes including the running game); /proc/pressure/irq is absent (no CONFIG_IRQ_TIME_ACCOUNTING); delay accounting is off (task_delayacct=0).** → Treat GPU meter, IRQ PSI and CPUD%/IOD%/SWAPD% columns as 'unsupported on this host' with a dash, mirroring htop; take per-process GPU data from NVML in the nvtop component.
- **Wide/tall content in a small grid cell: the process table and 32 per-core bars overflow easily, and Command must stay the elastic last column; braille/block glyphs may not render in some terminals.** → Footprint-aware degradation order, min-size checks before rendering, ASCII fallback set for bars/graphs (htop -U equivalent), horizontal scroll inside the table like htop's Left/Right.
- **Toolchain coupling: sysinfo 0.39.6 requires Rust 1.95 exactly matching torch's stable; an MSRV CI job lower than 1.95 (per astral-watch conventions) would fail if sysinfo is a hard dependency.** → Prefer procfs (MSRV 1.70) for core data; keep sysinfo optional behind a feature or pin an older line if MSRV must be lower; depend on libc 0.2.x not the 1.0 alpha.

## Open questions

- What is the grid unit (cols×rows per cell) and does the layout engine let a component declare min size per footprint? The 1x1/2x1/4x2/6x3 plan above assumes ~20×6 cells.
- Should the component expose sub-components (CPU meter, memory meter, process table) individually so users can place them separately, or only the composite htop tile with footprints? (Recommend composite first, split later.)
- Process actions in v0.x or deferred? If included, is a global `readonly` config plus a kill confirmation acceptable, and should renice/affinity/ioprio failures for root-owned processes offer a pkexec/sudo escalation path?
- Package watts: is the user willing to add a udev rule (chmod 0444 on intel-rapl:0/energy_uj) or run a small root helper/systemd service (astral-watch-style Prometheus exporter) so the CPU header can show power? Without one, RAPL is unreadable (0400 + perf_event_paranoid=4).
- Delay accounting columns (CPUD%/IOD%/SWAPD%): they need kernel.task_delayacct=1 and CAP_NET_ADMIN over taskstats netlink (a `neli`/`netlink-packet` implementation would be needed; not verified). Skip, or plan as a later arc?
- Is the 'AMD Ryzen 9 9950X3D2' with 2×96 MiB L3 correctly understood as dual-V-cache (both CCDs)? sysfs supports it, but the product is past my knowledge cutoff; confirm whether the UI should label CCDs 'V-cache' at all, or just show prefcore ranking/amd_x3d_mode.
- Sampler concurrency model for opsTui overall (std threads like astral-watch vs tokio): the htop sampler is synchronous file I/O either way, but the snapshot channel type depends on this decision.
- MSRV policy: sysinfo 0.39.6 needs Rust 1.95; if the CI MSRV job targets something older, sysinfo must be optional or an older line (0.35 needs 1.75, 0.37 needs 1.88).
