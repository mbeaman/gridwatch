## Major (1)

### Journal cannot serialise Datum::Record or &'static str ids, so record/replay (the arc-1 determinism test, fixtures, headless screenshots) cannot round-trip Record keys

The plan defines `Datum::Record(Arc<dyn Any + Send + Sync>)`, `MetricId { name: &'static str, .. }` and `SourceId(pub &'static str)`, and then specifies a JSON-Lines journal with 'one line per Msg::{Batch,Status,Alert}' plus replay via `apply_all`. `dyn Any` carries no Serialize/Deserialize, so every Record key (gpu.info, cpu.breakdown{n}, proc.table, audio.sink, net.route, net.conns, media.now, media.art, media.players, media.history) is unwritable, and `&'static str` names cannot be deserialised from an owned JSON line without a lookup table or Box::leak. Arc 1's own acceptance depends on this: the gpu `header` tier renders name/arch/cores from `gpu.info`, the determinism test replays torch-idle.jsonl through the full App, and `opstui shot --demo` renders the same tiers. Verified by reading §4.1/§4.5/§12 of the architecture; this is a type-level gap, not a crate limitation.

**Fix:** Replace `Arc<dyn Any + Send + Sync>` with `Arc<dyn RecordValue>` where `trait RecordValue: Any + Send + Sync + Debug { fn to_json(&self) -> serde_json::Value; fn as_any(&self) -> &dyn Any; }` (or erased_serde::Serialize), give the catalogue a static registry `name -> fn(serde_json::Value) -> Result<Arc<dyn RecordValue>>` populated by each `keys/<domain>.rs`, and intern metric/source names on deserialise by looking them up in that table (unknown names are skipped with a warning, never leaked). Add a journal round-trip unit test that covers every Record type in the catalogue, and keep `--tables off` as the size knob only for proc.table.

## Minor (6)

### cargo-deny licence allowlist fails on day one: ring (ISC) and webpki-roots (CDLA-Permissive-2.0) are unavoidable via ureq/rustls

`cargo info ring` → `Apache-2.0 AND ISC`; `cargo info webpki-roots` → `CDLA-Permissive-2.0`. ureq 3.4.0's default `rustls` feature expands to `rustls-no-provider + _ring + rustls-webpki-roots` (cargo info ureq@3.4.0), and astral-watch's non-optional ureq already drags them in: `cargo tree --offline` in the astral-watch checkout shows ring 0.17.14, rustls 0.23.40, rustls-webpki 0.103.13, webpki-roots 1.0.7. The plan's allowlist is 'MIT/Apache/BSD/CC0/Zlib/Unicode', so `cargo deny check` fails on the first CI run with the pins feature or ureq enabled. Separately, the 'no tokio without mpris/net-probe' deny job contradicts the feature matrix: `net-rdns` (hickory-resolver) and `net-dns` (zbus for resolved) each alone also require tokio.

**Fix:** Add `ISC` and `CDLA-Permissive-2.0` to `[licenses.allow]` (both permissive; or use `[[licenses.exceptions]]` scoped to ring and webpki-roots), and phrase the tokio assertion as 'no tokio unless any of mpris, net-probe, net-rdns, net-dns is enabled'. Run `cargo deny check` in arc 1 before the CI file is committed.

### crossterm is used by opstui-store and opstui-ui but is absent from [workspace.dependencies] and from their dependency lists

`Msg::Input(crossterm::event::Event)` lives in opstui-store and `Component::on_key(KeyEvent)` / `on_mouse(MouseEvent)` in opstui-ui, yet both crates are specified as depending only on ratatui-core/ratatui-widgets. crates.io dependency lists (fetched) show ratatui-core has no crossterm dependency and the facade's crossterm arrives only through the optional ratatui-crossterm; the workspace dependency table has no crossterm entry at all. As written, opstui-store and opstui-ui do not compile, and `--record-input` additionally needs crossterm's `serde` feature.

**Fix:** Add `crossterm = { version = "0.29", features = ["serde"] }` to `[workspace.dependencies]` and to opstui-store/opstui-ui (matching ratatui-crossterm's crossterm_0_29 so `cargo tree -d` stays clean), or define opstui-ui's own `Key`/`Mouse` event types and convert in opstui-app's input thread. Reword 'no TUI deps' for the store crate accordingly.

### ratatui-core 0.1.2 ships with default = [] (no std, serde, underline-color, layout-cache); a bare pin breaks per-crate builds of opstui-ui

`cargo info ratatui-core@0.1.2`: `default = []`, with `std`, `serde`, `underline-color`, `layout-cache`, `palette` all opt-in; `ratatui-widgets@0.3.2` default is `all-widgets = [calendar]` (pulls the `time` crate) and its `std` is separate. The plan pins `ratatui-core = "0.1.2"` / `ratatui-widgets = "0.3.2"` bare and enables `serde`/`palette` only on the facade in app+cli. `cargo test --workspace` unifies features so it would pass, but `cargo check -p opstui-ui`, the per-feature CI matrix and any future publish build ratatui-core without `serde` (theme `Color` (de)serialisation in opstui-ui fails to compile) and without `std`/`underline-color`/`layout-cache`.

**Fix:** Pin `ratatui-core = { version = "0.1.2", features = ["std", "serde", "underline-color", "layout-cache"] }` and `ratatui-widgets = { version = "0.3.2", default-features = false, features = ["std", "serde"] }` in the workspace table; add `cargo check -p opstui-store -p opstui-ui` (no workspace unification) to the CI matrix.

### Audio: --latency 512 changes the PipeWire graph quantum whenever the game is not running, so arc 4's 'no PipeWire quantum change' acceptance cannot hold as written

`pw-metadata -n settings` on torch: clock.quantum = 1024, clock.min-quantum = 32, clock.force-quantum = 0. A running capture stream requesting node.latency 512/48000 lowers the graph to 512 when no other node asks for less (the research's own note); today it is masked only because the game holds the sink at 256. The research also measured that pw-record's stdout cadence is 512-frame (4096-byte) chunks every ~10.6 ms for any --latency ≥ 512 because stdio buffering dominates, so 512 buys nothing over 1024. The exact command in the plan otherwise works: ran `pw-record --format f32 --rate 48000 --channels 2 --raw --latency 512 --target auto -P '{ stream.capture.sink = true, node.passive = true, node.name = "opstui audio" }' -n 2400 -` → 19 200 bytes. (Live quantum effect not exercised because the game currently pins it at 256.)

**Fix:** Default `latency = 1024` (same ~10.7 ms chunk cadence, no quantum change at the 1024 default), keep 512/`stdbuf -o0` as an opt-in 'low latency' setting, and rewrite the arc-4 acceptance as 'quantum unchanged at the default latency; ≤512 only while the widget is visible and low-latency is enabled'. Verify with `pw-top -b -n 1` while the visualizer is visible and no game is running.

### DSP: 64 log bands from a single N=2048 FFT are under-resolved below ~230 Hz — the lowest third of the bars share a handful of bins

At 48 kHz, N=2048 gives 23.4 Hz bins. 64 log bands over 30 Hz–16 kHz have ratio (16000/30)^(1/64) = 1.103, so band width = 0.103·f; that is below one bin until f ≈ 227 Hz, i.e. the first 21 of 64 bands (all the bass the retrowave look lives on) map onto ~10 bins, and the first 9 bands (30–70 Hz) share bins 1–3. N=4096 still leaves ~14 sub-bin bands. Both the spectrum tier (⌊(w+1)/3⌋ bars) and the Winamp 19-band vis 'resample the 64 bands', so they inherit blocky, duplicated bass bars. Arithmetic checked by hand against the plan's stated parameters.

**Fix:** Adopt cava's dual-FFT: N=8192 (5.9 Hz bins, 171 ms window) for bands below ~250 Hz and N=2048 above, both on the DSP thread (still trivial CPU with realfft), or reduce to ~48 bands from 40 Hz with webamp-style linear interpolation between neighbouring bins for sub-bin bands. Document that the published `audio.bands` vector is display resolution, not spectral resolution, and add a unit test feeding a 50 Hz sine that expects exactly one dominant low band.

### 'Exactly like astral-watch's tui.rs' is the wrong reference for terminal init: tui.rs calls ratatui::init(), which installs the restore-first panic hook the plan is avoiding

astral-watch src/tui.rs line 506: `let mut terminal = ratatui::init();`, lines 509–510 chain a second hook on top, line 546: `ratatui::restore()`. ratatui 0.30.2 src/init.rs (fetched from docs.rs) `set_panic_hook` is verbatim `let hook = take_hook(); set_hook(Box::new(move |info| { restore(); hook(info); }))`, and `try_init` enables only raw mode + alternate screen. So a future session that follows the plan's citation literally reintroduces the exact hazard §11/§16 call out: any contained source-thread panic under catch_unwind restores the terminal while the render thread keeps drawing.

**Fix:** Cite the actual sequence: `enable_raw_mode()`, `execute!(stdout(), EnterAlternateScreen, EnableMouseCapture)`, `Terminal::new(CrosstermBackend::new(stdout()))`, own restore on exit; never call ratatui::init/try_init/run. Enforce it with a clippy `disallowed-methods` entry for `ratatui::init`, `ratatui::try_init`, `ratatui::run` in clippy.toml so `-D warnings` catches a regression.
