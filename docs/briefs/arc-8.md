## Seam decisions made in this brief (D58) — implement as written, escalate if they do not fit

1. **The executor (`app/src/exec.rs`, seam 11).** One long-lived thread, owned by the app, fed by an `mpsc::Sender<(ActionId, Box<dyn Action>)>` and answering with `ControlMsg::Done(ActionId, Result<String, String>)` on the existing control channel — so a finished action reaches the store and the toasts through the path that already exists, and `--replay` replays it. The thread runs **one action at a time** in arrival order; an action that takes longer than `ACTION_TIMEOUT` (5 s) is not killed (we cannot kill a `kill(2)`) but its `Done` is reported as a timeout and the executor moves on. `Action::run` gains **no** `&ExecCx`: everything an action needs is captured when the component builds it, which keeps actions `Send + Debug` and testable without a machine. The shell refuses to send any action while `readonly` is set (the `--readonly` flag and the `readonly` config key), toasting *"read-only: <what it would have done>"* — the refusal is a `Warn` toast and a journal line, never a silent no-op.
2. **Confirmation is the shell's, not the component's.** A component returns `Command::Run` with an action whose `Debug` is the sentence a person will read. The shell shows a **one-line confirm bar** under the key bar — `kill -TERM 4242 firefox?  y/n` — captures the next key, and sends the action only on `y`/`Enter`. `Esc`/`n`/any other key cancels with an `Info` toast. Actions declare whether they need this: `trait Action { fn run(self: Box<Self>) -> Result<String, String>; fn confirm(&self) -> Option<String> { Some(format!("{self:?}?")) } }` — a `None` runs immediately (renice by one step, say), everything that signals or changes another process's scheduling asks. This is a seam change: it is in this brief, so it is decided, and it goes in the D58 entry.
3. **htop's `full` tier (zoom-only, `min 100×24`, `Chrome::Custom` for the F-key bar).** Built on what arc 2a already publishes; the new work is interaction, not parsing. Screens as tabs (**Main** and **I/O**, htop's two that make sense here — not htop's user-configurable screen set, which is a config surface nobody asked for yet); `/` incremental search (jumps the cursor, does not filter); `\` filter (hides non-matching rows, shows the filter in the F-key bar); `t` tree view (the parent map comes from `ProcRow.ppid`, which the scan already reads — the tree is a *sort*, computed in `tick`, never in `view`); Space tags a row, `U` clears tags, and an action applies to the tag set when it is not empty; `F` follow (the cursor sticks to a pid across sorts, and the tile says `following firefox (4242)`); `K` kernel threads and `H` userland threads, where `H` is what raises the source's demand to `Detail::Columns` and starts the `task/` walk (P15's ceiling applies to the walk, and the tile prints its cost like the `sources` tile does); the F-key bar draws through theme roles as a `View::Custom`, and it is the tier's signature. Sorting, selection and the column set stay exactly as arc 2a built them.
4. **The actions themselves (`components/htop/actions.rs`).** Four, each a small struct that captures a pid (or a tag set) and the numbers it needs: `Signal { pids, signal }` (`nix::sys::signal::kill`; `F9` opens htop's signal menu as an overlay list, `k` is `SIGTERM` directly), `Renice { pids, delta }` (`libc::setpriority`; `F7`/`F8` are ±1 and do not confirm), `Affinity { pid, mask }` (`nix::sched::sched_setaffinity`; `a` opens a CPU-mask picker), `IoPrio { pid, class, level }` (`libc::ioprio_set` through a tiny `unsafe`-free wrapper — the crate forbids `unsafe`, so this is a `libc::syscall` call in `app`, **not** in `components`, and the component's action holds only the numbers). Every one maps `EPERM` to *"not yours to change (EPERM)"* and `ESRCH` to *"it exited first"*. The gpu tile's `F9` reuses `Signal`.
5. **The gpu `full` tier's remainder.** `F6` sorts by any nvtop criterion, `+`/`−` cycle it, `h`/`l` scroll columns four at a time, and the Power sub-panel (already built in arc 3a) gains the pins-under-board-power comparison line. Nothing else changes: the tier exists and this is the interaction it was missing.
6. **The pins modes (`sources/pins`).** CSV tail mode and exporter mode both exist in code and neither has been verified against a running astral-watch. **An agent may not do this**: the exporter is a local HTTP endpoint (safe) but the CSV comes from the service that owns the i2c bus. Build the multi-card tab support (`[sources.pins] cards = [...]`, one tab per card in the tile, `Tab`/`Shift-Tab` between them) against the fixtures, write the verification steps into `docs/MACHINE.md`, and record both live rows as **owed to Matt**.
7. **The `exec` plugin host (`app/src/plugin/{mod,proto,supervise}.rs`, feature `plugins`, seam 12).** The protocol is §4.7 verbatim — do not redesign it. One child process per plugin instance kind, spawned with `Stdio::piped()`, **no shell** (`Command::new(argv[0]).args(&argv[1..])`, never a string through `sh -c`), a JSON line per message with a **1 MiB line cap** and a 64-message inbound queue that drops oldest with a `Warn` chip rather than growing. Supervision is a source's: backoff 1/2/4/8 s capped at 30, a restart counter, `Unavailable` with the reason on the tile. Every inbound line is validated against `schema/exec.schema.json` before it is looked at, and an unknown `kind` is a protocol error that counts toward a **three-strikes** rule (three malformed messages and the plugin is stopped, not restarted, with a `Crit` toast naming it). Resource caps: `RLIMIT_AS` and `RLIMIT_CPU` set on the child, and a supervisor check that kills a plugin over `plugin_rss_mb` (default 256) or 50 % of a core sustained for 10 s. A plugin's `View` is deserialised into the same `View` the built-ins return, so it cannot write cells, choose colours or reach a device — that containment is the whole reason the protocol returns a tree.
8. **The example plugin and the docs.** `plugins/examples/weather.py` — a source *and* a component in ~120 lines of Python 3 with no dependencies, reading a temperature from a file it makes up (no network, so CI can run it) — and `docs/PLUGINS.md` written for someone who has never read this repo. CI runs the example end to end: `gridwatch shot --page …` with the plugin placed, asserting the tile drew.
9. **Tests.** The executor: an `Action` that returns `Ok`/`Err`/panics (the thread survives a panicking action and reports it as an error), one that blocks past the timeout, and the `readonly` refusal — none of them touch a real process. The four real actions are tested against a **child this test spawned** (`std::process::Command` on `sleep 30`), never against anything else on the machine, and each asserts the observable effect (`/proc/<pid>` gone, `/proc/<pid>/stat`'s nice field, the affinity mask read back). htop's `full`: tier selection at 100×24 and zoomed 248×66, the tree's shape on a synthetic parent map, search and filter, tags with an action over the tag set, follow across a sort change, and `H` raising the demand to `Detail::Columns`. The plugin host: a fixture plugin in the test itself (a tiny Rust binary or a Python script under `tests/fixtures/`) covering hello/manifest/sample/render/view, a malformed line, an over-long line, a plugin that never speaks, one that dies immediately, and one that floods. Pty **C.26** (zoom htop, `/` search, `F9` cancelled with `Esc` — never confirmed), **C.27** (`--readonly` refuses an action with the toast), **C.28** (the example plugin renders).
10. **Performance.** P15 unchanged and re-measured with `H` on (the `task/` walk is the expensive path; the ceiling is the walk's ms, and it may only run at `Detail::Columns`); P19 for the zoomed `full` tiers; a new **P20**: the plugin host costs ≤ 1 % of a core with one example plugin at 1 Hz, and a plugin that floods costs the *host* nothing above that (the drop is the point). The executor is not on the render thread and must never block it — assert that in the shell test by sending an action that sleeps and checking frames still land.

## Gotchas already verified — do not rediscover
- `Command::Run` is declared in `crates/ui/src/component.rs:220` and handled **nowhere**; `ControlMsg::Done` exists and is likewise unhandled. Both are the executor's job, not a new seam.
- `Detail::Columns` already exists (`crates/store/src/source.rs:80`) and nothing raises demand to it yet. htop's `H` is its first user.
- The proprietary NVIDIA driver exposes no `drm-*` fdinfo lines, so htop 3.4's GPU column cannot be filled here. Say so; do not compute something plausible.
- `unsafe` is forbidden in every crate. `ioprio_set` has no `nix` binding; it goes in `app` through `libc::syscall` — and if that needs `unsafe`, it needs a `DECISIONS` entry and Matt's sign-off, not a quiet `allow`.
- The glob rule for any new filter is `store::rules::glob` (D57 amendment 9). There is one; do not write a fourth.
- Actions must never run against a process this project did not spawn, in any test, on any machine.
